# 04. 테스트 시나리오·결과서

> **이 문서의 역할**
> "이런 조건을 만들면 → 이렇게 동작해야 한다"를 미리 적어 두고, 실제로 해 본 결과를 기록합니다.
> 요구사항(01)이 모두 검증됐는지, FMEA(05)의 대책이 실제로 동작하는지를 이 문서에서 확인합니다.
>
> - 문서 버전: v0.6 (예시 초안 — 대피 단계, 고장·관제 로그 반영)
> - 담당: 통합·문서 (테스트 실행은 기능 담당과 같이)
> - 관련 문서: [01-requirements](01-requirements.md) · [02-state-machine](02-state-machine.md) · [03-interface](03-interface.md) · [05-fmea](05-fmea.md)

---

## 1. 이 문서 쓰는 법

1. **왼쪽 칸(사전 조건·절차·기대 결과)은 개발 전에** 씁니다. 개발자는 "무엇을 통과해야 하는지" 알고 만듭니다.
2. **오른쪽 칸(실제 결과·판정)은 테스트할 때마다** 채웁니다. 실제 결과에는 **테스트 시각(KST)과 DB 사고 번호(`incident_id`)**를 꼭 적습니다. 스냅샷이 있으면 파일 이름도 적습니다.
3. 기대 결과는 **숫자와 눈으로 확인할 수 있는 것**으로만 씁니다. ("잘 울린다" ✗ → "3초 안에 빨강 LED 깜빡임 + 부저 0.2초 주기" ✓)
4. 기준값을 바꾸거나 코드를 크게 고친 뒤에는 **전체를 다시 돌립니다** (회귀 테스트).
5. 히터로 실제 셀 온도(100℃·130℃)를 만들기 어려우면 **시연용 축소값**으로 시험하고, 그때 쓴 `config.yaml` 값을 실제 결과 칸에 같이 적습니다.

판정 표기: ✅ 통과 · ❌ 실패 · ⏸ 보류(장비 문제 등) · 빈칸 = 아직 안 함

## 2. 요구사항

요구사항(REQ) 목록과 내용은 [01-requirements](01-requirements.md)에 있습니다. 이 문서의 '검증' 칸은 그 번호를 가리킵니다.

## 3. 기준값 기호

테스트 표에서는 숫자 대신 기호를 씁니다. 기호·값·`config.yaml` 키는 **[02-state-machine](02-state-machine.md) 6번** 한 곳에만 적습니다. 기준값이 바뀌어도 테스트 표를 고칠 필요가 없게 하기 위해서입니다.
